# 如何让 Obsidian 成为 Claude Code 的大脑

## 编译摘要

### 1. 浓缩

- **核心结论1**: 作者个人实践主张通过L1持久画像、L2程序性经验、L3历史检索及按需加载改善复用与上下文占用；没有隔离文件结构、模型、任务、工具配置各因素的因果贡献
  - 关键证据: §01作者自述原memory.md 3000余行，每次读入约3万Token，改造后启动读入不到3000 Token；并非匹配实验或端到端费用。L2索引命中后读取，L3除了按请求检索，也会在开班按话题召回（§02）。
- **核心结论2**: Agent 从"每次对话重新猜测"变成"越用越像用户"，靠的是对话交班协议（5 步收班）+ 语义去重写入 + 项目级 PROGRESS.md 跨对话续接
  - 关键证据: §02语义去重是作者所述合并/追加逻辑，非无重复保证；三周后复用成功为单次自述。§03作者称项目brief约300字、不到500 Token，未测交接完整性、摘要误差或成本
- **核心结论3**: 工具发现靠"能力地图反向索引"（按"我要做什么"索引工具）+ Skill 封装工作流为肌肉记忆 + 三层 QA（动作自检 / PostToolUse Hooks / 定期体检）保障产出质量
  - 关键证据: §04作者自述5分钟、5000+ Token对比2秒、200 Token（无匹配对照）；§05描述每周Vault检查及每月Claude Code配置检查，原Raw未给14,287篇或6层的数量，撤出。动作回读、PostToolUse hooks及定期检查互补，不证明语义或最终业务结果均正确

### 2. 质疑

- **关于"三层记忆通用性"的质疑**: 作者的三层划分高度贴合个人开发者 + Obsidian Vault 场景。企业级 Agent 系统中，L1 用户画像可能涉及多人/多角色/权限分层，L2 程序性记忆可能涉及团队协作和版本冲突，L3 历史检索面临数据合规和审计要求。三层模型的扩展性需要更多验证
- **关于"语义去重可靠性"的质疑**: memory_update.py 的语义去重依赖 LLM 判断两条经验是否同义，但 LLM 判断本身有噪声。误合并可能丢失关键经验，漏合并也可能引入重复与冲突；按实际风险验证来源、适用范围及回滚
- **关于数据可靠性的质疑**: 文章是一人实践复盘，token 数据（3 万→3000、5000→200）缺乏控制组和可复现条件。收益可能受任务、模型、索引、工具版本及组织习惯共同影响，未量化各因素

### 3. 对标

- **跨域关联1**: 三层记忆（L1/L2/L3）可与情景、程序和语义记忆作有限类比；个人画像不是全部语义记忆，不证明与认知架构一一映射或演化方向
- **跨域关联2**: 能力地图反向索引类似 Unix `man -k`（apropos）命令——按"我要做什么"搜索工具，而非按工具名搜索。也类似 [[Agent-Harness]] 中"工具作用域策略"的一种实现
- **跨域关联3**: Skill 内化（提取设计思想 + 自己语料重组）类似 [[Knowledge-Compilation]]——不是搬运原始知识，而是编译为适合自己语境的版本
