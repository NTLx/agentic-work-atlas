# Agent 治理的三层保证：从表达层到机制层

> [!warning] 2026-11-28 知识消化修订
> 本文是设计分析框架，不是已经实证成立的三层保证定理。撤回原版“缺一即治理剧场”“L0 是规模化唯一路径”“强机制可代偿弱意图”“天级反馈即有效”等普遍命题，以及未核验的产品能力、监管因果与永久人类能力壁垒。历史版本可由 Git 恢复。

## 三层分别回答什么问题

| 层 | 问题 | 验收方式 |
|---|---|---|
| 意图层 L+ | 谁授权什么目标，谁承担后果，何时拒绝任务？ | 明确 owner、授权对象、风险边界、升级和冲突处理规则 |
| 表达与运行层 L1-L5 | 身份、权限、行为记录、运行监控及漂移如何表达和执行？ | 核对实际身份、可达工具及数据、策略执行路径和监控覆盖 |
| 机制层 L0 | 出现争议、绕过、失控或错误结果时，如何发现并处置？ | 验证独立于被监督 Agent 的证据、阻断和纠错路径 |

身份、权限策略与审计不只是表达：如果它们在正确的信任边界强制执行，就已经具有机制效力。三层是分析视角，而不是互斥技术栈。

## 机制层的三个关键问题

**裁决的独立性。** 对高影响争议，应确保被监督者不能自行决定证据和处置结果。独立性来自权限、职责分离、证据来源和可复核性，不必然要求每次由组织外第三方裁决。低风险操作可以采用机械判定和抽查；独立裁决本身也需监督。

**证据的可信性。** 哈希链、签名、访问隔离等可以帮助保护或检测日志完整性，但不能保证记录的事件真实、完整，或防止日志整体被删除、截断和重建。应区分采集覆盖、存储保护、外部时间或状态锚点、保留与检验。不能因为日志格式具有密码学结构就把记录当作事实。

**独立阻断与恢复。** 撤销不能依赖被撤销 Agent 的合作。应明确实际执行点、凭证撤销和在途任务处理；终止进程不等于撤回已经发生的外部写入、披露或支付。回滚和补偿需要单独的语义与权限设计，并测试不可逆结果。

## 意图与监督

可靠的执行机制不能弥补错误或未经授权的目标；积极参与的管理者也不能代替不可绕过的权限控制。两者解决不同问题。治理强度随影响范围、可逆性、可观察性和剩余风险配置，不能用固定审批次数、反馈周期或 Agent 数量作为有效性指标。

预防和适应需要并存：先阻止不能接受的动作，再监测实际执行、处理异常、校正策略，最后验证新策略确实解决问题且不扩大权限。反馈越快并不自动越好，错误归因与未经验证的自动修规则同样会造成风险。

## 权限棘轮的工程缓解

[[Permission-Ratchet-Mechanism]] 是解释长期授权撤销阻力的候选模型。任务级授权、短期凭证、默认失效与可审计续期可以缩小常驻权限窗口，但只有执行点真正检查过期、缓存和委派链才有效；续期与重授可能重新产生依赖。短期权限不会自动消除过度暴露的其他凭证。验收应测试到期前后、重放、并发及外部效果，而不仅是授权记录。

## 治理的最终锚点

技术控制服务于可问责的目标、可验证的执行和可纠正的结果。判断和建议可以部分委托给 AI，但责任归属与授权主体不能由模型自我声明。该结论是制度与架构设计原则，不是关于人类认知能力永久独占的事实判断。
