# Generation-Verification Asymmetry（生成-验证不对称）

> [!definition] 定义
> 生成能力提高时，验证需求可能增长得比验证容量快，导致瓶颈转移或未验收结果积累。这是条件性的工程与经济现象，不是验证不可自动化、生成成本趋零或债务守恒的普适定律。

## 四个诊断维度

| 维度 | 需要验证的问题 |
|---|---|
| 容量 | 单位时间生成量、验收吞吐、排队与返工 |
| 判据 | 任务语义、测试覆盖、参考有效性及实现正确性 |
| 认知 | 复核者的实际发现率、误判、时间与独立判断 |
| 组织 | 责任、授权、下游影响范围与修复资源 |

可复用的测试、确定性检查、形式证明、改进的判据与更好的生成质量都可能减少验证工作量。不同工作项的待验收状态、未覆盖风险与修复成本不能直接相加为守恒量。若衡量积压，先固定同口径工作单位及观察窗，分别统计新增、通过、拒绝/退役、重新打开与未完成；验收通过不代表未测风险已归零。

## 关键数据点：Lean kernel soundness bug #14576

[[20260801-lean-kernel-soundness-bug-postmortem]] 的作者事后报告（本轮实际回读本地 Raw 全文）：

- 2026-07-25 发布的 AI 辅助 Collatz “反证”并非有效证明；7-28 约简为小型反例并报告 #14576，作者称一小时后推出修复 #14577，随后合并、发布补丁。
- 原证明还通过了一周前的外部检查器 nanoda。作者将两处实现缺陷描述为无关，但未排除模型曾见过其中一个公开报告；不能据此估计缺陷统计独立性或攻击成本倍数。nanoda 的相关修复先于 Lean 报告，比较必须固定具体版本。
- lean4lean 的待验证实现继承参考实现缺陷，当时一致性证明尚未覆盖归纳类型；作者认为完成该部分验证时会发现问题，这是反事实判断，不是已完成形式证明。
- 报告记录回归测试、#14582 检查加固、额外六项 PR 与 nanoda 检查结果，以及每日跟踪上游和支持竞争性实现。这些是作者报告的局部响应，不是全部下游已重验、覆盖完备或净成本的独立测量。
- 作者的架构原则是 kernel 不依赖不可信 elaborator 拒绝不良声明。形式化保证受模型、假设、可信基及实际实现版本约束；测试、证明与实现多样性各有适用边界。

## 从修复到受影响结果的核验

1. 明确缺陷与受影响版本、任务及依赖范围，分别记录已知、不受影响和未知项。
2. 核对修复实际生效，使用适用的回归与独立检查，不能把 PR 合并或版本号变化视作所有结果已恢复。
3. 按影响面决定重验、撤回、替换或补偿；无须对明确不受影响的项作无边界重算。
4. 记录重验版本、判据、实际结果与剩余风险，无法确认的下游单列。

在明确范围内可以完成修复与重验；修复声明既不是全局保证，也不必然只是递延。不同验证实现可能减少某些共同缺陷，但新增实现也有维护成本，不能用实现数量或新鲜度代替覆盖与正确性测试。

## 前提与局限性

- 本页维持 mixed/medium：Lean 是局部实现与版本案例，宏观瓶颈模型为本库综合；没有比较生成和验证容量的纵向实测。
- 08-03 历史晋升及原理论见 [[2026-08-03]]；撤回四层不可扩容、验证债务守恒、修复声明必递延、形式域唯一清算、庞氏类比及∃/∀推导永久攻防速度差等。
- arXiv:2607.01904 仍为历史候选，本轮文件名搜索未找到明确身份，未核原文或完整注册表同义身份，不把它当量化证据，也不恢复旧工单。
- 检验假设应比较固定任务质量与风险条件下不同生成/验证配置的吞吐、成本、误判、返工、未知终态及后续缺陷，不以生成代码量或单次成功推断净效益。
