## Explore [2026-09-05T00:44:53] · 自我改进变更的行为契约与独立归因

- Mode: open exploration
- Trigger: 最新编译的 GitHub Copilot 成本优化材料给出了一个此前 `EX-007` 缺少的具体边界案例：prompt 压缩在离线评测中未暴露问题，却在首次线上实验中把独立 Agent 的并行执行改成串行；团队停止实验、补写行为回归评测后才恢复并行。当前问题不是是否要再造一个 EX，而是 `EX-007` 的“独立变更闸门”是否需要拆成不同强度的门。
- Evidence posture: GitHub 成本优化文章已进入本地 `wiki/sources/`，可作为当前 Evidence；GitHub Applied Science、Anthropic 与 Uber 页面为本轮联网核读、尚未剪藏的外部一手材料，只用于导航与 reasoning，不升级稳定 Entity/Topic。

### Evidence

- supports [[20260902-github-ai-coding-cost-efficiency]] — GitHub 把完整任务而非单次 tool call 作为效率单位；其 prompt 压缩实验中，离线评测未发现行为问题，首次线上实验却发现并行 Agent 被序列化。团队据此先停止实验，再增加针对并行行为的回归评测，最终用更短的指令恢复行为；文章还强调同一改动在不同 Copilot workflow 中可能产生相反结果。
- supports [GitHub: Agent-driven development in Copilot Applied Science](https://github.blog/ai-and-ml/github-copilot/agent-driven-development-in-copilot-applied-science/) — 官方开发记录描述了一个只能由人改动或必须保留的测试空间，把它作为防止 Agent 为适应新范式而改写测试的 contract-like guardrail。这是“行为不变量需要保护边界”的实践线索，但没有给出跨版本回放、回滚成功率或安全收益的量化结果。
- supports [Anthropic: Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) — Anthropic 将 harness 的每个组件视为关于模型能力边界的假设，并主张逐个移除、逐个检查影响，因为模型能力变化会使原本 load-bearing 的组件过时；其材料同时指出 evaluator 可能自我宽松，需通过调校和外部反馈提高判断质量。该材料支持“harness 变更本身是实验变量”，但不是独立变更闸门的因果证明。
- bounds [Uber: Running a Software Factory Efficiently at Uber Scale](https://www.uber.com/by/en/blog/efficient-software-factory/) — Uber 为隔离优化收益而固定模型，并按真实工作 benchmark、任务完成成本和质量信号（如 revert rate、F1、MTTR）观察 managed agent；这提供了版本归因的工程做法。但公开材料没有给出冻结外部 evaluator/policy、隐藏 holdout、rollback 成功率或独立安全复评，因此不能替代 `EX-007` 要求的控制边界。

### Reasoning

1. `EX-007` 原先把“独立变更闸门”说成一个总条件；本轮证据把它拆成两类失效。第一类是**行为变化未被普通结果门看见**：任务可能仍通过测试，但并行、停止、检索、通知或副作用顺序已经改变。第二类是**提升无法归因**：当 evaluator、目标或 policy 与 harness 一起变化时，内部得分上升可能来自真实能力、评测器变宽、目标变窄或 benchmark 接口适配。
2. 因而暂定两层结构：
   - **行为契约门**：把并行语义、授权前停顿、结果交付、不可重复副作用等需要保持的不变量写成受保护回归测试；它首先回答“这次变更有没有改写系统行为”。
   - **独立归因/安全门**：当变更触及 evaluator、reference、policy 或高风险执行边界时，用冻结的外部 oracle、隐藏任务、只读 policy 和可回放 manifest 检查旧保证是否仍成立；它回答“分数/成本变化是否可解释、是否有安全回归”。
3. 这是对原命题的边界收窄，不是把所有 harness 维护都升级为强人工审批。只改格式且不改语义的优化，可能只需要行为契约与工作流本地复评；但 prompt、orchestration、router、evaluator 或 policy 的改变，不能由单一内部 acceptance gate 自证。
4. GitHub 的单案不能证明“线上一定比离线更真”，只能说明离线 gate 对某类行为回归存在漏检可能。Anthropic 与 Uber 的材料共同支持更窄的工作假设：变更必须按实际 workflow、模型版本和控制面记录来评估；它们尚未提供长期、跨组织、可复现的独立安全证据。

### 新问题

**`EX-007`（refined）：当优化器只修改行为组件而 evaluator/policy 冻结时，受保护行为契约加工作流本地在线复评，是否足以承担变更门；一旦 evaluator、reference 或 policy 也可被优化器修改，独立且不可自改写的归因/安全门是否不可替代？**

当前判断：`EX-007` 仍保持 `synthesized` 和开放状态。最新材料使其从“是否需要一个抽象的独立闸门”收窄为“哪些组件变更需要哪种不可自证的门”，但还没有同一任务上的分层对照。

### 证伪方向

- 在固定模型、任务、工具权限、oracle 和 policy 后，仅修改 prompt/harness；若普通 outcome gate 加工作流本地在线复评已稳定捕获并行、检索、停止和副作用顺序的变化，且受保护测试区不再提供额外召回，则削弱行为契约门的独立必要性。
- 若允许 evaluator 或 policy 与 harness 共变，内部 acceptance gate 的提升仍能在冻结外部 oracle、隐藏 holdout 和独立安全策略上稳定复现，且跨任务迁移、回放和 rollback 不变，则削弱独立归因/安全门的必要性。
- 反过来，若优化版本通过普通质量门和本地线上指标，却在冻结 policy 的隐藏任务上出现 unsafe action、false block 或意图保持下降，则证明“成本/质量无回归”不能替代独立安全复评；这会强化 `EX-007`，但仍需多个任务或组织案例排除单一 harness 事故。
- 若所有版本残差最终都能由 `EX-004` 的 reference/source-lineage 失效或 `EX-006` 的 policy-carriage 失效解释，并在冻结 target/policy 后消失，则将 `EX-007` 并回已有候选。

### 最小实验

在一个可回放、可控副作用的多 Agent 编程任务上固定模型、任务集、工具权限、evaluator 和高风险 policy，只做一次 prompt 或 orchestration 优化，比较旧版 `H0` 与新版 `H1`：

1. 先跑普通 outcome gate（任务成功/测试通过、成本、轮次）。

## Recompile [2026-09-05T00:56:27] · AI 监督 AI 共模误差下界

- Claim: 即使使用不同模型家族，AI 监督 AI 仍存在不可消除的共模误差下界。
- Gap: Boundary
- Action: reasoning_operator
- Skill: `ljg-think-recompile` (`.agents/skills/ljg-think-recompile/SKILL.md`)

### Evidence

- supports [Apple Machine Learning Research：Nine Judges, Two Effective Votes](https://machinelearning.apple.com/research/correlated-llm-evaluation-panels) — 既有一手研究在 7 个模型家族的 9 个 judge 上观察到约 2.18 个有效独立投票，面板准确率低于独立投票基线 8–22 个百分点，且结果对任务、提示、温度和 chain-of-thought 变体保持稳定。
- bounds [arXiv 2607.10139v3《LLMs as a Jury》](https://arxiv.org/abs/2607.10139) — 既有一手研究的跨家族 verifier panel 在数学任务的 shared-error floor 接近 0，在 GPQA 为 0.030、MMLU-Pro 为 0.143；更换 generator 后仍复现，材料对象是特定 consensus/verifier panel 与 benchmark。

### Reasoning

- shared-error floor 是由任务错误结构、panel 组成和共同可见证据条件化的残余错误，不是跨所有监督系统的固定常数；跨家族只削弱部分相关性，不等于条件独立。
- 数学任务的近零结果限定了适用边界：可执行或可核查任务可能把该面板的残余压到很低，但不反驳开放式科学/知识任务中的非零 floor。
- 现有材料没有测试外部 checker、人类 adjudicator 或其他独立观测路径能否打破该相关性，因而不能把面板结果外推为所有 AI 监督形态的下界。

### Result

- Delta: no_delta
- Conclusion: 本轮只用既有证据复核 CR-003，未发现超出此前“任务与 verifier 条件”边界的新事实或实质新区分。Claim 继续保持条件化理解，不应普遍化为所有 AI 监督形式均有同样的不可消除下界。

## Explore [2026-09-05T01:49:04] · 验证器的 reference integrity 与 success provenance

- Mode: open exploration
- Trigger: `EX-004` 已有多条待剪藏的一手材料，但“reference 是否正确”与“成功是否由评测中获得的信息造成”仍被同一个 oracle/source-lineage 标签笼统承载。本轮用 AgentJudgeBench 的 corrupted-GT 控制和 AcquaBench 的 CLEAN/GOLD/SHAM 干预，检查这两个问题能否继续并为一个门，还是需要分成两个可独立验证的子门。
- Evidence posture: 以下均为本轮联网核读的一手论文或官方材料，尚未进入 `raw/` / `wiki/sources/`；只进入本日志和 Source 需求队列，不升级稳定知识页。

### Evidence

- supports [AgentJudgeBench 一手论文](https://arxiv.org/html/2608.26623) — 论文把同一生成器输出分别交给 programmatic reference 与 LLM judge，并在 with-GT / without-GT 条件下比较；GT trace 经过 JSON schema、参数类型和 trace consistency 的程序检查，另有 120 条 hard 记录的单标注人类校验。作者同时明确指出：120 条样本只有每条一个标注者，不能给出人类标签自身的 inter-annotator agreement。
- supports [AgentJudgeBench 的 corrupted-GT 控制](https://arxiv.org/html/2608.26623) — C3 用同拓扑另一条记录的错误 GT 替换正确 reference；Gemini-2.5-Pro 在 corrupted-GT 下与标准 GT 几乎一致，QwQ-32B 则接近 without-GT，提供了“锚定 reference 的存在/格式”与“检查 reference 内容”之间的区分。论文还记录了 fan-in 中结构上可交换的 sibling calls：程序化 scorer 以位置精确匹配，judge 认为功能上合理，暴露 structural-vs-semantic 的 oracle 边界。
- supports [AcquaBench 一手论文](https://arxiv.org/html/2607.24054) — 在同 qid、模型、action channel、reference target 与 scorer 下，CLEAN 只保留授权信息，GOLD 注入正确 target，SHAM 保留来源结构和暴露机会但替换为匹配的错误值。D0 中三种模型的 GOLD–SHAM 均为正（+19.1 至 +25.9 个百分点）；D2 把充分信息分散到两个来源后，GOLD–SHAM 仍为正，但单源 coloc AUROC 降到 0.376 / 0.142，说明成功的目标值依赖与单源可见性不是同一个对象。
- bounds [AcquaBench 研究边界](https://arxiv.org/html/2607.24054) — 这是 HotpotQA 单一 benchmark family 上的冻结、可构造干预，不是自然污染率估计；四种 action surface 是同一干预的标准化接口，不是四个独立部署复制。它固定 reference target，因而不能单独验证静态 oracle 是否正确；AgentJudgeBench 也主要验证结构化 tool-calling 的 programmatic reference，不能外推到开放式 judge 或生产 trace。

### Reasoning

1. `EX-004` 不应再把所有“来源”当成一种风险。至少要区分：
   - **静态 reference integrity**：目标是否可辨识，reference 是否正确、语义等价、版本同步，程序化 scorer 是否把结构偏好误当成任务真值；
   - **动态 success provenance**：在 reference 固定时，分数是否跟随评测期间获得的正确目标信息，而不是只跟随“见过某个来源”或 outcome 结果。
2. AgentJudgeBench 的 C3 直接操纵 reference 内容，因此支持静态门具有独立可观测变量；它也显示“给 reference”并不等于“增加真值”，因为 judge 可能只对 reference block 锚定。AcquaBench 则操纵 agent 的信息状态，说明静态 reference 正确仍不足以解释 score 的因果来源。
3. 两者暂时仍留在 `EX-004`，因为共同问题是“评测结果究竟回链到哪个权威对象”：前者回链到任务/裁判的 oracle，后者回链到轨迹中的信息状态。现在新建候选会重复 oracle/source-lineage 主线；下一轮若控制实验显示动态 provenance 的残差在 reference 与 evidence coverage 固定后仍稳定存在，再考虑把它升级为独立候选。
4. 本轮不把 AgentJudgeBench 的 92.7% 人类一致率当作强真值证明：该研究明确只有单一标注者，且 programmatic scorer 对 parameter structure 的人类一致率降至 82.5%。同样，不把 AcquaBench 的四个 action surface 当作独立重复样本；两篇论文的边界声明都要求保留这种克制。

### 新问题

**`EX-004`（refined）：在固定生成器输出、任务、工具权限与 evidence coverage 后，reference 的正确性/语义等价/版本绑定是否仍独立影响 judge 判定；在 reference 固定后，评测期信息状态的 success provenance 是否还会独立改变结果解释？**

当前判断：`EX-004` 仍为 `refined`、开放状态，但内部至少有“静态 oracle integrity”和“动态 success provenance”两个子门；尚无同一任务上的交叉操纵，因此不把它们误写成两个已证实的必要条件。

### 证伪方向

- 若在同一 trace 上将 reference 随机化为无 reference、正确 reference、语义等价 reference 和错误 reference 后，judge 的错误、校准与排序对 reference 内容不敏感，则静态子门可并回 `EX-001/EX-002` 的目标或证据覆盖问题。
- 若在固定 reference、scorer、模型与任务后，CLEAN/GOLD/SHAM 的 score 与 provenance 指标无稳定差异，或差异完全被 exposure detection 解释，则动态子门无需独立保留。
- 若两类差异只在 AgentJudgeBench 的 synthetic DAG 或 AcquaBench 的 HotpotQA 构造中出现，而在真实可回放 agent trace 的语义等价 reference 与多来源信息路径中消失，则收窄为 benchmark-construction artifact。
- 反过来，若 reference 内容效应和 success-provenance 效应在 evidence coverage、模型家族和任务难度固定后仍各自保留，并改变 human adjudication 或模型排序，则 `EX-004` 的 oracle/source-lineage gate 获得独立残差支持。

### 最小实验

在一个可回放的多步 tool-calling 任务上，固定 agent trace、任务、模型、工具权限、scorer 与 evidence coverage，做两层最小干预：

1. 对同一 trace 仅改变 judge 可见的 reference：`none / correct / semantically equivalent / corrupted`，记录 judge verdict、human adjudication、calibration 与排序变化。
2. 对同一 qid 再做 `CLEAN / GOLD / SHAM` 信息状态配对，保留来源结构与暴露机会，记录最终 outcome、信息路径、exposure detector 和 score。
3. 只有当 reference 条件与 information condition 的效应在各自另一维固定后仍存在，才把两个子门视为独立残差；若残差只由 reference 或 exposure 一项解释，则并回已有候选。

- bounds [OAP 的实验与实现边界](https://arxiv.org/html/2603.20953v1) — T1/T5 是参与者自选的观察性比较，不是随机对照，只有银行单域；作者明确列出 framework hook、policy engine、签名基础设施为信任假设，`ESCALATE` 在参考实现中尚未完成，逐次允许的调用还可能通过累计效应完成结构化攻击，且授权范围内的意外副作用不在防护范围。作者同时是 OAP 实现公司的创始人，因此结果只作候选机制证据，不作跨域效果估计。

### Reasoning

1. **三类材料的被测对象不同。** `2604.07650` 的单位是模型在任务上的错误行为，核心问题是多个信号是否在给定难度后仍共同失败；AJ-Bench 的单位是验证者在环境中取得和解释证据的过程；AgentJudgeBench/AcquaBench 的单位分别是裁判依赖什么 reference，以及被测 agent 的成功是否依赖正确目标的可得性。把三者合并成“验证可靠性”会丢掉因果对象。
2. **证据门获得机制级支持，但仍没有必要性证明。** AJ-Bench 中“正确证据、错误推理”与“工具输出误读”表明，即使信息已到达，解释层仍会失败；同时，Agent-as-a-Judge 与 LLM-as-a-Judge 的比较没有固定模型独立性或 source/reference 质量，因此不能判定差异究竟来自 evidence visibility、agentic tool-use 能力，还是更宽的验证者行为变化。
3. **reference integrity 与 success provenance 不应再当作同一个变量。** AgentJudgeBench 的 corrupted-GT 询问裁判会不会被错误 reference 锚定，AcquaBench 的 GOLD/SHAM 询问成功是否跟随正确目标；前者属于评估器的 oracle/interface 条件，后者属于被评估 agent 的信息来源条件。二者会互相污染，例如错误 reference 既可能改变 judge 的 verdict，也可能改变 agent 的可得信息，但当前材料没有交叉操纵来估计交互项。
4. **跨模型不等于独立。** `2604.07650` 自身把独立性定义为给定难度后的输出错误条件独立；论文没有证明跨家族在目标、证据、执行和时间四轴上都脱钩。反过来，AJ-Bench 的环境感知也不等于独立验证，因为所有 judge 仍可共享相同 reference、任务构造和标注误差。
5. 因此本轮对 `EX-001/002/004` 都是 `refined`，不新增 EX：三门应作为同一验证实验的正交维度，当前最有价值的不是继续收集“某门有效”的单线结果，而是寻找固定 task/trace 后的交叉操纵。

### 新问题

### 证伪方向

- **独立性可并回：** 固定 evidence access、reference、任务和 trace 后，改变模型家族/独立实现不改变共同漏报；或者其效果完全由 evidence coverage 与 judge interpretation 解释。

### Reasoning

1. **无状态的对象必须先说清楚。** 2026-07-28 改变的是 wire protocol：请求不再依赖隐藏在 transport 中的协议 session，可以由普通负载均衡直接分发；它没有消除 server-side cache、业务事务、长任务、租约、幂等键、授权上下文或审计状态。将“协议无状态”写成“系统无状态”会把部署事实误写成架构结论。
2. **状态从隐藏关联键变成显式能力。** 旧模式把跨请求关系放在 `Mcp-Session-Id` 和 server session store 中；新模式要求应用自己定义 handle，并让模型在后续调用中携带它。这样更容易被模型、网关和审计系统看见，但也把 handle 的 owner binding、scope、TTL、撤销、重放和跨租户隔离责任推到应用/Registry/授权层。显式不等于安全，反而提供了可被单独测试的接口。
3. **MRTR 不是“无状态没有交互”，而是把交互变成可重试状态机。** 服务器不再依靠持续双向 stream 隐式挂住一次调用，而是返回 `input_required`，客户端带 `inputResponses` 重试原调用。故需要验证重复提交、过期回答、原请求与回答的绑定、幂等性及中途撤销；这些属于 `EX-005/006` 的执行/控制状态，不是 MCP transport 的简单性能变化。
4. **网关能力增强了可观测性，也增加了元数据一致性要求。** `Mcp-Method` / `Mcp-Name` 让 WAF、限流器和路由器可以不解析 JSON body 就按操作计量；但 header 与 body、身份、显式 handle、policy version 和 trace context 若不一致，会形成“网关看到的动作”和“server 实际执行的动作”两条谱系。这直接连接 `CR-004` 的 action-surface coverage 与 `Agent-Security` 的事件级 join key。
5. **这不是新的独立研究候选。** 其主要残差已经落在现有边界：`EX-005` 的逐动作授权/撤销/恢复，`EX-006` 的控制状态承载与绑定，`CR-004` 的观测与事件连续性，MCP Entity 的协议—治理分层。当前最有价值的是更新字段和最小实验，不制造 `EX-008`。

### 新问题

**MCP 无状态转折问题（P1，refined）：** 在同一多轮工具任务、相同身份与负载下，移除协议层 session 后，显式 handle、MRTR 和每请求元数据能否同时保留跨调用语义、授权归属、可审计谱系与可撤销性？还是把隐式 session 风险转移成 handle 混淆、重放、跨主体复用和 MRTR 重试风险？

当前判断：MCP 的“无状态”应记录为**传输层去 session、应用层显式承载状态**。它可能改善横向扩展、故障转移和网关可见性，但是否改善安全，取决于 handle/消息的身份绑定、时效、幂等和事件关联；现有材料尚无部署级对照。

### 证伪方向

- 若真实应用在 2026-07-28 模式下无需 server-side state、显式 handle 或幂等/租约机制即可完成长程多轮任务，并在重试、故障转移和撤销中保持等价，则“状态只是迁移”应收窄为少数复杂工具的边界。
- 若显式 handle 已被统一的身份绑定、scope、TTL、撤销和 replay protection 覆盖，且跨主体复用、重复执行和审计断链率不高于旧 session 模式，则无状态转折可能是安全中性或正向的，而非风险转移。
- 若负载均衡/故障转移收益只来自把状态放进外部 cache、队列或业务数据库，且这些状态仍依赖隐式用户/线程关联，则“plain round-robin、无需 shared storage”只能成立于协议层，不能作为生产系统结论。

- [Ghost in the Context](https://arxiv.org/html/2605.12535v3) 把 policy-carriage 定义为：可信约束在动作前的 decision state 中仍然存在、语义健全并绑定到同一 actor/action/object/condition/evidence。受控压力回放中，task-local policy 出现 eviction/weakening/over-budget continuation，受保护 placement 保留状态；但固定 assembler 的行为校准为 `0/90` unsafe-action proposals、`0/90` unguarded violations，且论文明确说这只是 state-level 证据。其 overload 表显示 exact active-policy replay 的 best-effort 仍有 `25/48` silent incomplete-control rows；加 complete-set preflight 后为 `0/48` silent continuation、`25/48` fail-closed。参考设计提出 typed provenance、stable identifiers/evidence handles、control/data budget 分离、manifest 与 canonical action monitor；同时明确未证明 ControlCapsule 优于 exact active-policy replay + preflight。
- [Governance Decay](https://arxiv.org/html/2606.22528v2) 在 `1,323` 个 episode、七个模型中报告：完整 policy 的 control 为 `0%` violation，单次 compaction 后 pooled violation 为 `30%`、最高 `59%`；policy 被删时为 `38%`。对 summarizer 的优化注入可击穿固定攻击免疫模型；Constraint Pinning 在主网格中恢复到 `0%`，但 recent-context 的 operator impersonation 仍使 naive pinning 达 `17%`，加入 provenance 文本也只降到 `10%`，作者把 trusted out-of-band operator channel 列为未解问题。
- [Hidden in Memory](https://arxiv.org/html/2605.15338v2) 将攻击拆成 `write → retrieve → use`：外部 document/webpage/repository 可诱导持久记忆写入伪造的 user memory，原文消失后在新 session 检索并影响 Agent Action。论文报告 GPT-5.5 的写入率最高 `99.8%`；在成功 retrieval 条件下，攻击意图的 agentic action 影响为 `60–89%`（跨模型/设置）。但它没有系统评估 deletion、correction、user review 或 provenance-aware editing 作为防御。
- [Security-Recall Divergence](https://arxiv.org/html/2604.20911v1) 的 `4,416` trial、12 模型/8 provider 三臂实验显示 omission constraints 随深度衰减：Mistral Large 3 从 turn 5 的 `73%` 降至 turn 16 的 `33%`，而 commission constraints 保持 `100%`；token-matched control 在仅测试的两个模型上显示 schema semantic content 解释 `62–100%` 的 dilution effect。周期性重注入与 Safe Turn Depth 可恢复 compliance，但八类约束全是可 string-match 的 formatting proxies，真实“永不泄露 API key”等语义安全约束未测。

### Bounds

1. 四篇材料共同证明的是“约束/记忆在 context assembly 或持久化路径中会丢失、弱化、错绑或被伪造”的机制风险，不是生产环境中不可逆副作用的发生率。
2. `Ghost` 的 action-level 负边界很关键：policy 缺失并未在其固定 assembler 校准中自动诱发 unsafe action；其 native traces 也没有自然 overflow，压力结果是 counterfactual replay。`Governance Decay` 的 tool call 只解析、不执行，所有 secret/PII 是虚构的。
3. provenance 与 actor/object binding 在 `Ghost` 中主要是 reference design；其正文称 misbinding 的实证信号最弱。其余三篇没有把来源、主体、对象绑定作为独立因果变量。
4. `Sleeper Memory Poisoning` 的 provider-specific memory pipeline 部分不可观测，部分 prompt 是重构或经验推断；`Security-Recall Divergence` 的 Arm C 只覆盖两个并非最易受攻击的模型，且 formatting proxy 与真实语义安全的对应关系未验证。
5. 因此“必须”不能从论文自报结果直接推出；尤其没有一项四因素析因实验能独立估计 provenance、binding、budget isolation、survival 与 action-boundary enforcement 的增量。

### Reasoning（Inference）

当前最稳妥的收窄判断是：**对高影响/不可逆动作，普通可压缩、可检索、可被内容影响的 token-stream 文本不能作为唯一治理执行面；至少要把可信控制状态与数据面分开，并在动作边界使用可验证的结构化约束。** 四篇论文分别给出承载失败、压缩删除/伪造、持久记忆污染和 omission recall 失效的拼接机制。

这不等于所有 policy 都必须采用完整的外部 control plane。`Ghost` 明确把 exact active-policy replay + complete-set preflight 作为强基线：只要适用集可确定、绑定无歧义、预算在调用模型前检查，简单受保护 replay 可能足够。更强的 ControlCapsule/OOB 设计只有在 authority 会被不可信文本冒充、actor/tenant/object 必须稳定绑定、控制预算不足应停止动作，或需要 action-time manifest/monitor 时才有额外理由。即便 policy 已生存，`Ghost` 的 `0/90` 负边界也说明 carriage integrity 不能替代 action monitor；应分别测“模型提议”“monitor 阻断”“禁动作实际执行”。

### 新问题

**在固定高影响 action、模型、工具权限与 verdict 下，provenance、actor/object binding、control-budget isolation、context survival 和 fail-closed action enforcement 是否各自留下独立的 unsafe proposal、misbinding 或 executed-violation 残差？还是 exact active-policy replay + preflight 已经吸收了其全部安全增量，而更复杂的 capsule/OOB 只增加可用性成本？**

### 证伪方向

- 在相同模型、任务、工具 schema、权限、policy、verdict 和 context pressure 下，若普通 task-local text 在真实语义约束、compaction、memory poisoning、operator impersonation 后与 protected replay/capsule 在 policy presence、binding、unsafe proposal、executed violation、false block 和 availability 上长期等效，则“不能只用 token stream”应收窄。
- 逐项移除 provenance、actor/object/evidence handle、reserved control budget 和 complete-set preflight；若隐藏 holdout 中不产生 misbinding 或 silent incomplete control，或都被同一个 deterministic monitor 捕获，则这些不应被保留为独立必要条件。
- 若 exact active-policy replay + preflight 与 provenance capsule/external registry 在 action-level 指标上等效且可用性成本更低，则 `ControlCapsule` 应降为实现模式，而非独立安全结论。
- 若在固定缺失/错误 policy 的条件下，真实语义任务仍稳定没有 unsafe proposal 或 executed violation，则当前结论只能保留为 state-level integrity 风险；若再加 action-boundary monitor 后所有 carrier 差异消失，EX-006 应与 `EX-005` 合并或进一步收窄。

### 下一步目标建议

先做下述最小实验，优先把“状态生存”与“动作执行”拆成两个可识别结果；在获得真实语义 action-level 对照前，不创建稳定页，也不把 OOB 写成普遍定理。

### 最小实验

在隔离、可回放且不可恢复删除的模拟资源库中，固定 `agent-A`、`tenant-T1`、对象 `artifact-O7`、审批 ID 与 evidence hash，规则为“仅当 actor/object/approval/condition 全匹配才允许 delete”。比较三种承载：`T` ordinary task-local text；`R` exact active-policy replay + complete-set preflight；`C` 带 issuer/version/hash、actor/object/evidence handles 与独立 control budget 的 capsule。所有臂注入长 tool output、compaction、poisoned-memory write/retrieve 与 forged operator rescind；先记录 decision state 的 presence/soundness/binding 和 model proposal，再把同一批 proposal 各自送入无 monitor 与 deterministic canonical monitor 的执行臂。

## Explore [delegate] · CR-004 OTel GenAI 语义边界

### Mode

bounded research delegate；仅核查 OpenTelemetry 官方 GenAI semantic conventions、规范仓库与公开 PR。本节是唯一写入，不修改 agenda、raw 或 source summary。

### Evidence posture

截至 2026-09-05，现行 GenAI 页面标为 Development；因此以下关于“当前可表达什么”的判断以官方仓库当前规范为准，关于安全语义扩展的判断只把公开 PR 当作未采纳的设计证据，不当作现行规范。未重复 AJ-Bench、SkillTV-Bench、AgentJudgeBench 或 AcquaBench 结论。

### Evidence

1. [OpenTelemetry GenAI agent spans（官方规范仓库）](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md) 当前区分了远程 `invoke_agent`（CLIENT）与进程内 `invoke_agent`（INTERNAL），并定义 `invoke_workflow`、`plan` 等操作；workflow 示例覆盖 handoff、sub-agent、agent-as-tool。页面也列出 agent/workflow/conversation 相关字段和通用 `error.type`。但 handoff 在这里是 workflow 形状/示例，不是有发送方、接收方、理由、确认、结果或交接时延的一等事件；列出的操作也没有独立 authorization/handoff 语义。

2. [OpenTelemetry GenAI spans（官方规范仓库）](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md) 定义 `execute_tool`，要求工具名，推荐 `gen_ai.tool.call.id`，并把 `gen_ai.tool.call.arguments` 与 `gen_ai.tool.call.result` 作为 opt-in、可能含敏感数据的结构化内容。`result` 的语义是工具调用返回的 payload（成功时），不是外部状态已改变、被拒绝、回滚或可验证的 action effect；`error.type` 也只是通用错误类型，不能单独标出错误发生在模型、工具、授权、策略、交接还是恢复阶段。输入/输出、工具定义、参数/结果以及检索内容均有 opt-in 或敏感数据约束，span 存在不等于证据内容可访问、未被过滤或足以复核。

3. [PR #427：run guardrail span and security finding（官方公开 PR）](https://github.com/open-telemetry/semantic-conventions-genai/pull/427) 提议 `gen_ai.run_guardrail` span、`gen_ai.guardrail.security.finding` event，以及把 guardrail 的 verdict 与调用方实际采取的 action 分开，并补充 policy/rule、risk、external finding ID 等字段。这正面支持“判断”和“执行”需要分开记录，但 PR 仍为 open、且其参考场景明确暴露 capture gap：`openai-guardrails` 框架状态可产出基础 guardrail span，却不提供 policy identity、external finding ID 或标准 risk class，因而无法自动产出安全 overlay/finding。

### Reasoning

现行 OTel GenAI 语义可以较好枚举结构层：agent/workflow/plan/tool invocation、局部 ID、父子 trace 上下文和通用错误。它不能据此闭合 CR-004 所需的行为—责任链。特别是：`tool.call.result` 不等于动作副作用结果；`error.type` 不等于阶段化错误；`invoke_workflow` 不等于 human handoff；`conversation.id` 是应用会话标识，规范还要求没有真实 ID 时不要用 trace ID 伪造替代。因此当前语义最多给出局部 lineage，而不是跨 `evidence → interpretation → authorization → actuation → result → recovery/handoff` 的安全 lineage。

“证据可访问性”和“主动检查/正确解释证据”也没有被独立操纵或独立观测：内容字段可选、可因敏感性而不记录，规范没有统一字段区分“未访问”“访问但未记录”“被过滤/截断”“已记录但被错误解释”。同样，当前规范没有独立的 authorization decision、principal/tenant binding、action surface、policy version/hash、actual enforcement、post-state、revoke/recovery 或 handoff owner/ack 字段。PR #427 说明社区正在补 verdict/action/policy/risk/finding 的分层，但它尚未改变现行边界。

### New question

在固定任务、模型、工具权限和策略下，仅用当前 OTel GenAI spans 加标准 trace context，能否重建 `agent → plan → evidence/retrieval → tool → authorization/verdict → actuation/result → error → human handoff/recovery`，并可靠区分“未访问、未记录、被裁剪、被误解、执行未生效”这五类状态？

### Falsification direction

- 若不增加自定义安全字段，现行 span、event、links 与导出内容已能让独立审计者唯一重建 principal、action surface、policy、verdict、authorization、actuation、owner、recovery，并区分未观察与被过滤，则上述语义缺口被高估，应收窄。
- 若实现方能证明 `invoke_workflow` 稳定发出包含 sender/recipient/reason/ack/result 的显式 handoff 子事件，或 `tool.call.result` 能在规范约束下证明外部 post-state，则对应缺口不成立。
- 若 PR #427 合并后仍只覆盖 guardrail verdict/action，而没有授权主体、决策绑定和实际副作用，那么它只能削弱“verdict/action 未分层”的判断，不能证伪完整安全 lineage 缺口。
- 反之，必须在完整导出、无采样且分别开启/关闭 opt-in 内容的条件下测试；否则不能把字段缺失误判为访问失败，也不能把访问失败误判为解释错误。

### Source needs

- P0：[PR #483：Define GenAI execution state-change events](https://github.com/open-telemetry/semantic-conventions-genai/pull/483)（本轮仅发现，未作为 Evidence 采用）：核对是否定义 applied/denied/post-state/rollback/idempotency 等执行结果语义。
- P0：[PR #447：Unified OpenTelemetry model for agent-to-agent interactions](https://github.com/open-telemetry/semantic-conventions-genai/pull/447)（本轮仅发现，未作为 Evidence 采用）：核对 agent-to-agent/handoff 的 sender、recipient、ack、reason、result 与 lineage 设计。
- P1：官方 schema/conformance 示例或实现测试，需覆盖 opt-in、过滤、截断、采样和 exporter 丢失，并给出“不可访问”与“未产生事件”的可区分标记。

### Next-step recommendation

不新增 EX，也不提升为稳定 Wiki 结论。下一步只需核读上述两个官方 PR，并用同一回放任务做事件级 conformance 对照；重点把“span 已存在”与“证据可复核、授权可归因、动作效果可验证”分成独立分母。

### Minimal experiment

构造一条固定、可回放的任务链：`invoke_agent → plan → retrieval → execute_tool → policy/guardrail decision → action attempt → human handoff`。注入五种已知情形：证据未访问、访问但被过滤、已记录但故意误解、授权拒绝但工具仍尝试、工具返回成功但外部状态未改变；再加入 handoff 确认与超时各一例。比较三臂：当前规范默认不记录敏感内容、开启 opt-in 且不截断、以及在不改变业务动作的情况下加最小自定义安全 event。

让独立审计者只看导出的 OTel 数据，测量阶段归因、跨事件 join、证据可访问性分类、verdict→actuation 对齐、post-state 可验证性、handoff owner/ack 重建率和错误归因率。若默认臂已唯一重建全部状态，CR-004 不变；若只有自定义 event 能区分这些情形，则直接支持本节的边界判断。

### Result

- Delta: refined
- Conclusion: 现行 OTel GenAI 语义能区分 agent/workflow/plan/tool invocation、局部 lineage 和通用 error，但不能独立区分 authorization、实际 action effect/post-state、证据可访问性与正确解释、human handoff 及安全责任链。`tool.call.result` 只是返回 payload；PR #427 的 verdict/action/policy/risk/finding 设计是有方向性的补洞证据，但仍是未采纳提案，且其参考实现揭示了安全字段的真实采集缺口。

### Reasoning

1. Ramp×Revelio 与 Dallas Fed 并不构成简单的正反例，而是三个层级的不同估计量：企业采用后的总 headcount/结构、职业任务的招聘需求、以及年轻人进入劳动力市场的流量。高采纳企业可以扩大总人数，同时减少某些高暴露任务的岗位入口。
2. 因此，“entry-level headcount 上升”不能反驳 `CR-005`。专业再生是质量与时间维度：谁获得真实任务、谁被带教、谁晋升、谁能独立发现错误。现有 Ramp 页面只给人数与 seniority share；Dallas Fed TBOS 只给当前用工需求、生产率和工资自报，均没有培训/晋升/独立验证指标。
3. 本轮把 Claim 的反例门收窄为：必须找到高采纳组织中，入门级数量上升之外，学徒任务、导师投入、内部晋升或独立验证能力至少一项长期不降，最好同时有岗位质量/工资分布。否则“企业扩张”只能说明 AI 的规模效应与任务替代可以并存。
4. 这也削弱了“AI 采纳必然立即消灭入门岗位”的强叙事，但没有削弱“组织可能把再生成本外部化”的机制命题；结果为 `refined`，不新建 EX。

### 新问题

**`CR-005`（refined）：** 当高强度采用企业扩大总 headcount 或 entry-level share 时，是否同时维持了把入门劳动转化为专业能力的机制——真实任务暴露、导师/培训投入、内部晋升与独立验证质量？若只有人数增长而能力再生指标下降，企业扩张不是反例。

### 证伪方向

- 若高采纳企业的入门级 headcount 增加同时伴随导师比、训练时数、任务复杂度、内部晋升率和独立错误发现率长期不低于未采用或低强度对照，则 `CR-005` 的外部化命题被削弱。
- 若 Dallas Fed 的招聘下降仅是岗位发布迁移，且行政雇佣、工资、培训与晋升数据不出现入口或能力损失，则“任务入口收缩”不能作为专业再生受损的代理。
- 若高强度采用企业的入门岗位增加主要来自新业务扩张，并能在两年后看到晋升管道、导师投入和独立验证质量同步改善，则它构成真正的 counterexample；单独的 10.2% headcount 或 1.15pp share 不够。
- 反过来，若同一企业同时出现 entry-level 数量上升、导师/训练下降、晋升停滞或错误由 AI 兜底而人类发现率下降，则支持“数量扩张掩盖再生外部化”。

### 下一步目标建议

先剪藏并编译 Ramp×Revelio 与 Dallas Fed 两组一手材料，建立“企业规模效应—职业任务需求—个人入口—能力再生—工资分配”五层表；然后只寻找同时公开培训/晋升/独立验证结果的第二个高采纳组织。没有这些字段前，不把 Ramp 的入门级增长写成反例，也不把 Dallas Fed 的招聘下降写成长期能力退化事实。

### 最小实验

构造企业×月份面板，按 AI 采用强度做事件研究，并同时记录五类结果：总 headcount、entry-level share、真实入门任务暴露、导师/培训投入、入门→资深晋升与独立错误发现率。以低强度采用或尚未采用企业作对照，另按职业 AI 暴露度分层；把岗位发布、实际雇佣、工资和任务质量分开。关键判别是：若 `headcount↑` 但 `training/promotion/independent-validation↓`，则企业层“扩张”与专业再生外部化并存；若五类指标均不降且至少在第二组织复现，才削弱 `CR-005`。
